# iMessage capability matrix (macOS 26)

What a line can do in Messages on a macOS 26 guest, how MessagePilot does it, and the evidence behind each claim. Lines runs macOS 26.6.2 guests (macOS 27 guests can't use iMessage), so every row targets that version. Recorded 2026-10-25.

## New-account identity fix

**Bug:** Beeper's `CurrentUser.fetch` reads `SELECT DISTINCT account_login FROM chat`. A brand-new account has no chats, so it reports `default` and the worker exited with "Observed Messages account does not match expected identity".

**Fix (`native/Sources/MessagePilotKit/Identity.swift`, `IdentityCheck` in `Main.swift`):**

1. Messages history first. If any `chat.account_login` matches, accept (source `chat.account_login`). If history exists for a _different_ identity, fail closed as before.
2. With no history at all, read the active Identity Services (iMessage registration) account in `~/Library/Accounts/Accounts4.sqlite`. Its Apple ID, vetted aliases and registered `mailto:`/`tel:` handles are compared after normalization (case, `E:`/`P:` prefixes, US `+1`). DSIDs never match.
3. Last, ask Messages over AppleScript for its iMessage accounts (Lines already grants Automation).

`identity` now reports `identityCheck` with the matched source. Beeper keeps the `default` placeholder as the sender ID of own messages until the next worker restart; `isSender` stays correct.

**Evidence:** 11 Swift unit tests, including an Accounts store built with the real table and archived-property shapes. A TypeScript test runs the compiled binary's `--resolve-identity` against fixture databases. On a real Mac, an empty chat.db plus the real Accounts store resolved through `ids-account`, and real history resolved through `chat.account_login` ([probe](evidence/identity-probe.json)). Still assumed: that a Messages-only sign-in in a macOS 26 guest (no system Apple Account, see Lines B5) creates the same Identity Services record. If it doesn't, step 3 applies. Live test L2 confirms this on the next new line.

## Secure-input vault (a DOOR iMessage app)

Goal: like GamePigeon, the line sends an interactive bubble with a button. The person taps it, the line's app opens with a field, and the pasted value goes straight to the line's backend over HTTPS with a one-time token. The bubble turns into "Connected". The value never enters the transcript, and no AI reads it.

### (a) Can a macOS 26 guest send the bubble, and what does an iPhone without the app see?

**The line's Mac can send it once the extension is installed in the guest.** Only the app that created an `MSMessage` can send it. Without private APIs (others do this with LLDB and ChatKit with SIP disabled; Lines keeps SIP on), the extension must run in the guest's Messages:

- Apple documents `MSMessagesAppViewController`, `MSMessage`, `MSSession` and `MSMessageLiveLayout` for Mac Catalyst 13.1+ (Messages framework 14.0+).
- Mac Messages hosts extensions of the same `com.apple.message-payload-provider` point with platform "Mac Catalyst". Apple's own (#images, Apple Cash, Game Center, Image Playground, Memoji) are installed that way.
- `apple/Vault` builds for Mac Catalyst with that extension point and `UIDeviceFamily` 6.
- MessagePilot already reaches it: `apps.messages.open {app: "DOOR"}` → `apps.interact setValue` on `vault.requestLink` → press `vault.sendRequest` → press `sendButton`. Messages stages extension messages in the composer. In the Simulator both the request and the update waited for Send, and `sendButton` is the same identifier the Mac effect flow uses.

Not yet proven live on a macOS 26 guest, because that needs the app installed in a line's VM (V1).

**The person never opens the app drawer.** Tapping the bubble opens the extension with that message selected. The harness tapped the bubble and got the secure field in the expanded view directly.

**iPhones without the app:** Messages shows the bubble's alternate template layout (image, "Connect Lofty API key", "Tap to paste it securely"). Apple says that layout is "required to represent your message on devices that don't have your iMessage app installed". The secure field can't open without the app. When the app is on the App Store, Messages offers its store page; the payload carries the app's App Store ID. A TestFlight-only build has no store page, so recipients must already have the TestFlight build. On a Mac without the app, selecting the bubble opens its URL in a browser (Apple's `MSMessage.url` note). The bubble URL is the reference server's HTTPS fallback page, which reads the token from the URL fragment, so a browser never sends it to a server.

### (c) Minimal working project

`apple/Vault` (XcodeGen; `xcodegen generate`):

- `LineVaultMessages` is the Messages extension (iOS + Mac Catalyst). Line side: a compose view takes a request link and sends an interactive `MSMessage` with a new `MSSession`. Person side: tapping the bubble opens a `SecureField`. The value is POSTed with the bubble's one-time token and Messages' per-device participant UUID over an ephemeral `URLSession`. On 200 the same session is updated to "Connected", and that URL carries no token. Only hosts listed in `VAULT_ALLOWED_HOSTS` are accepted, so a look-alike bubble can't collect secrets. `VAULT_DISPLAY_NAME` brands it (for example DOOR).
- `LineVault` is the containing app. `LineVaultTests` (4 unit tests) and `LineVaultFlow` (the Simulator harness) are the test targets.
- Backend: `node dist/src/cli.js vault-server` (`src/vault.ts`). An admin-only mint returns the bubble URL with the token in the fragment. Submits are single-use, time-limited (default 15 min) and locked after 5 bad tokens. Values are encrypted at rest with AES-256-GCM and readable only through the server-side `reveal()`, never over HTTP and never as an agent operation. Status shows `pending` / `connected` / `expired` only. There's also a fallback web page. 4 Node tests.

**Simulator evidence (iOS 26.5, `LineVaultFlow/testBubbleFlow`, passes):** the extension is opened from the add menu, the request link is entered, the staged bubble is sent, the person taps it, the value is typed, Connect is pressed, and the staged update is sent. The bubble shows "Lofty API key connected", and the backend reports `connected` with the device UUID. A search of the Simulator's entire data directory found the dummy value only in runningboard's log of the UI-test runner's launch environment (how the harness passed it). No Messages store, extension container or preference contained it, and the backend store holds only ciphertext (WAL included). Screenshots: [compose](evidence/vault-1-line-compose.png), [line confirms Send](evidence/vault-2-line-confirms-send.png), [bubble](evidence/vault-3-bubble-in-transcript.png), [person opens bubble](evidence/vault-4-person-opens-bubble.png), [update staged](evidence/vault-5-update-staged.png), [connected](evidence/vault-6-bubble-connected.png).

Two behaviors worth knowing:

- On iOS 26.5 the "Connected" update was staged, and the person tapped Send once more. Apple's `send(_:)` sends automatically only right after a user touch, and the network round trip falls outside that. The backend is already `connected` before that tap.
- The pending bubble's URL (with the one-time token) is in the line's own chat.db, so the line's AI could see the token. It can't learn the secret from it. At worst it could spend the token before the person does; the status would then show `connected` from an unexpected device UUID.

## What Lines needs to change

1. **Ship the gateway and worker together** from this branch (`MP_SRC=… ./bundle.sh`). The gateway validates every operation a worker advertises, so a new worker under an old gateway is rejected at hello. Bumping the kit `VERSION` makes each guest's slot agent restart its worker; schedule that.
2. **Guest config (`Guest/slot-agent.js` native.json):** `enableUIAutomation` defaults to `enableExperimentalEffects` (already true). Add `enableFiles: true` so Lines can `files.write` media into the workspace without enabling computer tools (B7).
3. **Agent API and tools:** `/lines/{id}/command` already reaches every new operation. Friendlier endpoints and `lines-mcp.mjs` tools are needed for:
   - reactions: `/react` with any emoji (its doc lists only six names) and `messages.sticker.attach`
   - `messages.sticker`, `messages.schedule` / `scheduled.list` / `scheduled.cancel`, `messages.forward`
   - formatting: `messages.format` (B8)
   - files: `media.create` + `files.write` + `messages.send {filePath | filePaths}` (B7, B5 contact card)
   - attachments: `attachments.download` and attachment metadata in inbound webhooks (B4, B6)
   - `messages.get`, `messages.reactions`, group management, `apps.messages.*`
4. **Inbound events (B3/B4/B6):** forward Beeper's `attachments[]` (with `isSticker` / `isVoiceNote`) and sticker reactions to the agent. The agent then calls `attachments.download`.
5. **Identity:** no change. Drop the "send one message first" step from PLAN.md once L2 passes.
6. **Vault:**
   - Host the vault backend on HTTPS (Tailscale Funnel or the line's domain).
   - Add an agent tool that mints a request through the admin API.
   - Install the signed Mac Catalyst app in the master image.
   - Drive the send through `apps.messages.open` / `apps.interact`.
   - Deliver status changes to the agent without the value.
   - Let only the server-side integration (Lofty) call `reveal()`.

## SIP

No code changes SIP, AMFI, library validation or Messages injection settings. Everything above uses Accessibility, AppleScript, read-only database access and the public Messages framework. Private ChatKit sending, which is how some services send iMessage app payloads from a Mac, requires SIP to be disabled and is not used.

## Performance design

A resident Swift process avoids per-message process startup. Persistent WebSockets avoid polling for command dispatch. SQLite WAL with full synchronization preserves command intent before dispatch. Messages are serialized per account because they share a desktop. Development builds use a separate lane. UI flows wait on chat.db reconciliation, not fixed sleeps, and never press Send twice.

## Extension webhooks

[Invites, Location and Check In workflows](EXTENSION_WEBHOOKS.md) have authenticated request/claim/observation endpoints and MCP tools, with signed durable callbacks. Callback delivery, agent observations and native success remain distinct verification levels.
