# Developer behavior patterns

These patterns make MessagePilot tools predictable during long or consequential work. The bridge supplies transport and state primitives; the developer's application supplies workflow decisions.

| Pattern               | Recommended behavior                                                                                        | Existing support / remaining work                                                                                                                                    |
| --------------------- | ----------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Quiet progress        | Report meaningful milestones; coalesce rapid updates; reserve a final summary.                              | Implemented by [progress jobs](PROGRESS.md), within native edit limits.                                                                                              |
| Output receipt        | Finish with a concise summary and named files. Preserve originals for reuse.                                | Progress attachment manifests, file storage and versioned library exist. Native paths and gateway file IDs remain different storage locations.                       |
| Waiting for input     | State exactly what is needed, then resume after an explicit response.                                       | Progress `waiting` state and interactive cards exist. Application must implement the approval policy and bind replies to the right job.                              |
| Cancellation          | Provide a Cancel action, propagate it to running tools, report what completed before cancellation.          | A producer can report `cancelled`. End-to-end cancellation tokens, a Cancel button and tool interruption policy are recommended additions.                           |
| Stale-task detection  | Track heartbeats separately from meaningful progress. Say “no update received” before assuming failure.     | Job timestamps and last-update display exist. Heartbeat expiry, deadlines and watchdog alerts are not implemented by progress jobs.                                  |
| Retry and recovery    | Retry known-safe requests with the same key; stop on ambiguous native outcomes.                             | Persistent commands, content-sensitive idempotency, revision checks and unknown-outcome stops exist. Operator reconciliation UI and progress resume are future work. |
| Preview before action | Render a draft or proposed change, including recipient and files, before a developer-defined approval gate. | Cards/control leases and scoped tool calls are building blocks. This is not a universal approval engine.                                                             |
| Honest completion     | Separate accepted, executing, completed, delivered and read. State what was created and what failed.        | Command and progress transport receipts exist; read/delivery analytics require real observations.                                                                    |
| Useful errors         | Give a short user explanation and a correlation/job ID; keep technical diagnostics out of the conversation. | Job IDs and command IDs exist. Rich error redaction and operator support views remain application responsibilities.                                                  |
| Chat budgets          | Set per-chat context, usage and notification budgets; avoid overwhelming a group with each tool call.       | Exact-chat scope, optional analytics/context limits and progress throttling exist. General cost budgets and notification quotas are not implemented here.            |
| Checkpoint and reuse  | Persist intermediate artifacts, link their provenance, resume from known checkpoints.                       | Versioned backend library and file references exist. The developer owns durable workflow scheduling and checkpoint semantics.                                        |

For this product, cancellation propagation, heartbeat/deadline handling and approval cards are the most useful next shared behaviors. They belong beside progress as explicit modules rather than being hidden inside individual tools.
